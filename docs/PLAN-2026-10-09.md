## 2. Eligibility and backend

Creator rules specify accepted activities, target IDs, cutoff and reward terms. Default semantics for alternative activities are OR: any valid qualifying route can approve the user. Explicit repeated-support rules can require distinct events across dates. No route becomes required simply because a recipe exists.

Flow: connect platform → consented inspection of accepted routes → identify candidate → prove it → server validates → evaluate rule → eligibility result. If a route has no qualifying event, try another accepted route. A technical/source error remains a technical/source error, not proof of ineligibility. Stop unnecessary collection once sufficient evidence qualifies unless the user opted into a broader support record.

Implement a common record containing platform, source subject, activity type, target, verified artist/channel relationship, original activity time and precision, observed/proved time, event identity, provider version/hash and coverage. Keep raw private history out of public responses and logs. Support records created before campaigns.

Server requirements:

- Validate signatures, trusted attestor/provider version and request/body/recipe hashes; ignore client-supplied eligibility.
- Bind the proof request to a one-time Early session and authenticated wallet; establish source-account ownership separately. Reclaim proof-owner key is not automatically the Privy wallet.
- Reject account A identity combined with account B activity, wrong target, mixed-item fields, edited dates, stale/reused sessions and duplicated events.
- Store normalized evidence and versioned rule evaluations durably; repeated proof submissions must be idempotent.
- Use deterministic cutoff comparison with explicit timezone/precision. A cutoff overlap is indeterminate. “Early” means qualifying activity before a stated cutoff, not global fan rank or first-ever discovery.

## 3. Monad, Privy and Envio

Monad: implement a small funded native-testnet-token benefit escrow. Creators fund a benefit with a fixed payout/capacity; eligible fans claim once; unused funds become refundable under explicit expiry/closure rules. Do not imply that token payout alone implements actual ticket or merchandise fulfillment.

Use server-signed EIP-712 claim authorizations bound to chain, contract, benefit, beneficiary wallet, amount, expiry and a benefit-scoped source nullifier. Contract checks signature, funding, capacity, expiry and duplicate consumption; update state before transfer and protect against reentrancy. The trust model is explicit: the contract trusts Early's eligibility signer, not direct independent verification of every source fact. Do not put source IDs or raw activity/proofs on-chain.

Required contract tests: valid funding/claim/refund, invalid signer, wrong chain/contract/benefit/wallet, changed amount, expired authorization, duplicate claims including wallet changes, insufficient funds/capacity, unauthorized or premature refunds, failed transfer and reentrancy. Inspect legacy code; do not carry Base/Zama assumptions into the new path.

Privy: actual embedded-wallet funding, claim and refund transactions on Monad testnet, with network, gas, pending, rejected and failed transaction states. Login alone is insufficient. Verify current SDK/network setup during implementation. Test tokens only; obtain any missing deployment credentials through secure local handling.

Envio: index benefit-created/funded, claim-paid and refund/closure events from the real contract. Drive displayed remaining funding/capacity, claim history and creator totals from the index. Handle indexing delay and event reprocessing/reorgs; show pending status instead of false failure. Contract state remains authoritative for spending. Installation alone is not the integration.
